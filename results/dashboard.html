What this is

A small but real compiler stack for tensor programs: a graph IR, an operator-fusion pass, two codegen backends (portable C, hand-written AVX-512), a real autotuning search that verifies every candidate before trusting it, a calibrated and a learned cost model, a real ONNX frontend validated against onnxruntime, a real PyTorch comparison, a transformer FFN block with fused LayerNorm, fused multi-head attention, a fused backward kernel, a Go service for sharing tuning results across processes, and a random-graph fuzzer that stress-tests correctness far beyond hand-picked test cases, subgraph fusion for diamond patterns like Sigmoid(h)*Tanh(h), row-broadcast Conv+bias+ReLU fusion, and a general reverse-mode autodiff engine for arbitrary fused chains.

Transformer block: LayerNorm fusion

A real post-norm FFN sublayer: LayerNorm(x + Linear2(GELU(Linear1(x)))). The residual-add + normalize pattern is fused into one single-pass kernel — the same idea FasterTransformer and DeepSpeed-Inference call AddLayerNorm. Capstone: full multi-head self-attention, verified bit-exact against PyTorch's own production module

The single hardest, most valuable fusion target in a real transformer compiler is attention — the entire reason FlashAttention exists. A fused, numerically-stable softmax kernel plus a real multi-head self-attention forward pass are assembled with the existing GELU fusion and the AddLayerNorm kernel into a complete transformer encoder layer, checked against torch.nn.TransformerEncoderLayer itself — not a hand-rolled reference, the actual module used in production:

max diff vs real torch.nn.TransformerEncoderLayer: 1.19e-06

Verified across 4 configurations including odd non-power-of-2 dimensions (d_model=96, nhead=6, seq=17, batch=3) — all pass.

The first version of the softmax kernel was 5–15x slower than PyTorch — diagnosed using this project's own established theory: a naive scalar expf loop loses to a vectorized library exp, the same reason a chain containing Sigmoid lost earlier in this project. The fix was one compiler flag change (-ffast-math -lmvec, linking glibc's real SIMD-vectorized exp):

At the full encoder-layer level this project still runs ~1.6–2.4x behind PyTorch eager mode; with the kernel now fast, that gap traces cleanly to Python-level orchestration overhead (reshapes, multiple numpy calls for head-splitting), not kernel quality — a real, identified next target, not a mystery.

A cost model that got WORSE before it got better

The first fix for a known misprediction (a binary transcendental flag couldn't tell Tanh from Sigmoid) made accuracy worse, not better — 56% instead of 88%. The reason was a real ML lesson: holding out the only Tanh-containing sequence meant the model had zero training signal for that feature, so its learned weight was exactly 0.000. No amount of extra parameters fixes a feature the model never sees vary. The actual fix was adding genuine Tanh signal from other sequences — not more features, more data:

Five more additions, one honestly reverted

Subgraph fusion: Sigmoid(h)*Tanh(h) — the exact diamond pattern documented as excluded for correctness reasons — is now genuinely fused into one kernel, verified on the graph that originally motivated the exclusion.

Conv+bias+ReLU row-broadcast fusion: Conv2D's bias varies per-channel, the opposite broadcast axis from every other kernel here. Verified against real torch.nn.functional.conv2d+relu (9.5e-7 diff), 4.5–9.5x faster than numpy in isolation.

Attention orchestration — disproven and reverted. The documented hypothesis blamed "Python orchestration overhead" for the PyTorch gap. Building the fix and measuring it in isolation proved the hypothesis wrong: numpy's reshape/transpose were already free (lazy views), and the "fusion" kernel was 100–400x slower for eagerly copying data that was never being copied. Reverted rather than shipped as a false win — real profiling data recorded instead, pointing at PyTorch's internal matmul fusion as the actual (still open) source.

General autodiff engine: reverse-mode backward for any chain of Add/Mul/Sub/Neg/ReLU/Sigmoid/Tanh/GELU, verified against real PyTorch autograd across 5 sequences. Found two more real bugs building it — a buffer overflow, then the exact same row-offset indexing mistake as bug #4. Both fixed; 5–6.9x faster than naive numpy backward.

Bug #9: the mirror image of bug #4, found independently by the grown fuzzer

Extending the fuzzer to cover diamond patterns and LayerNorm found a new bug almost immediately: a fusion pass written this session fused an ordinary bias-add into AddLayerNorm as if it were a genuine residual connection — the exact same class of mistake as bug #4, independently reintroduced in different code. Silent NaN, not a crash. Fixed the same way, then the fix revealed the fuzzer had zero real coverage of the mechanism the bug lived in — a dedicated grammar rule was added to guarantee it:

All nine real bugs, caught by testing before they shipped

1. Fan-in through a computed activation
The fusion pass initially let Sigmoid(h) * Tanh(h) get folded in as if the second operand were a broadcast bias vector.
Fixed by requiring a binary op's operand to originate specifically from a Param node.
2. Autotuning "cache" recompiling on every hit
The JSON cache stored the winning config, but every lookup still invoked a fresh gcc subprocess.
Fixed with in-process kernel memoization — a cache hit became a dict lookup.
3. Compiled kernel coupled to IR tensor names
Two real MLP layers sharing the same op-signature but different bias tensors broke the kernel cache.
Fixed by making the C ABI purely positional — a kernel never needed to know IR names at all.
4. Residual connection fused as a broadcast bias
Add(ff, x) in a transformer residual got treated like a (cols,) bias vector — x is a full 2D tensor, so the kernel silently read only row 0 for every row.
Fixed by tightening the eligibility rule to require the operand's origin be a Param, not just "not elementwise."
5. Fusion pass skip-set ordering bug
fuse_add_layernorm computed which nodes to skip only when it reached the LayerNorm node — but the Add node it needed to skip had already been emitted earlier in the same forward pass.
Fixed with a proper two-pass rewrite: decide first, then build the output list.
6. Silent float32 → float64 promotion
erf(v / np.sqrt(2.0)) divided by a Python float64 scalar, silently upcasting the whole array — which then corrupted memory when handed to a strictly-typed float32 C kernel.
Fixed the cast at the source, and added dtype assertions at every ctypes boundary so this class of bug can never again fail silently.
7. A plain units bug in the PyTorch benchmark
Multiplied an already-millisecond value by 1000 again, making results look 1000x worse than reality.
Caught immediately by the numbers being obviously implausible — fixed and re-verified.
8. Silent data corruption via in-place buffer aliasing — found by fuzzing, not by hand
A compiled kernel mutated its input buffer in place for performance. A shared Input feeding both a fusible chain and a later, separate MatMul got silently corrupted — no error, just a wrong number. The only bug of the eight that would have shipped silently; a random-graph fuzzer (the same technique as Csmith/NNSmith) found it in the first 20 generated cases.
Fixed by tracking root-exclusivity from use-counts already computed during fusion (zero extra cost) instead of always copying defensively — verified clean across 1000 random graphs with zero performance regression on any existing benchmark.
9. A residual-add mistaken for a bias-add — the mirror image of bug #4, found independently in a different fusion pass
A new pass, fuse_add_layernorm, fused Add(x, bias) into AddLayerNorm whenever an Add fed a LayerNorm, without checking whether the second operand was a genuine full-tensor residual or an ordinary (cols,) bias Param. The kernel assumed both operands were full (rows, cols) tensors; handed a (64,) bias for a (29, 64) input, it read past the small array for every row past the first — silent NaN, not a crash. Found by the extended fuzzer, which also revealed the fuzzer had zero actual coverage of this fusion path until a dedicated grammar rule was added.
Fixed the same way as bug #4: require the second operand to originate from something other than a Param before treating it as a broadcast-eligible residual. Verified clean across 1000 random graphs genuinely exercising all three fusion mechanisms (217 elementwise + 843 diamond + 851 AddLayerNorm fusions).
